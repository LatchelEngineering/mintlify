Every product release that changes what customers see needs a matching help guide. Data Support owns that work, and most of it is now automated. Each morning, Claude checks the previous day's **#product-release** posts against help.latchel.com and drafts the guide changes. We review the drafts, open one pull request, and merge it. The tracker sheet and the Slack announcement then update on their own.

<Check>
  **In other words:**

  Claude drafts the changes at 6:00 AM PT. We review them on the review page, click **Create pull request** once, and merge the PR in GitHub. Everything after the merge happens automatically.
</Check>

<Warning>
  The automated steps run as Claude scheduled tasks on the Data Support Lead's computer, and they only run while the Claude desktop app is open there. If the app is closed at 6:00 AM, the check runs the next time it opens and catches up on any days it missed.
</Warning>

## **How the Routine Works**

| When | What happens | Who |
| --- | --- | --- |
| **Every day, 6:00 AM PT** | Claude reads the previous day's #product-release posts (and new replies on release threads from the last 30 days), compares them with the help guides, and drafts updates or new guides. It adds **one entry** for the day to the Help Guide Release Review page and logs each release in the tracker sheet. Days with no releases are skipped. | Automatic |
| **During the day** | Review the day's entry, edit the drafts if needed, and click **Create pull request**. All of the day's changes go into one pull request. | Data Support |
| **When it's ready** | Review the pull request in GitHub and merge it. Merging is what publishes the changes. | Data Support Lead |
| **Every hour, 7:00 AM–8:00 PM PT** | The sync marks merged rows **Published** with the date. Once the changes are live, it posts one announcement per pull request in **#help-center-announcements**. | Automatic |

## **How to Review and Publish the Day's Drafts**

<Steps>
  <Step title="Open the day's entry." icon="1" iconType="sharp-solid" stepNumber={1} titleSize="h4">
    Open the Help Guide Release Review page and choose the entry under **To review**, for example **Releases from Oct 21 (3 posts)**. Entries with a pull request already move to **Pull request opened**.
  </Step>
  <Step title="Read each draft." icon="2" iconType="sharp-solid" stepNumber={2} titleSize="h4">
    Each draft shows the source release, the target article, and a one-line summary.

    - **Updates** show the current text next to the new text.
    - **New guides** show a preview, or click **Edit MDX** to change the title, description, or content.
    - Read the **Open questions** box. It lists anything the release post didn't make clear, like a button name or a missing screenshot.
  </Step>
  <Step title="Choose what goes in." icon="3" iconType="sharp-solid" stepNumber={3} titleSize="h4">
    Tick **Include in PR** for every draft that's ready. Drafts marked **Needs info** start unticked. Leave them out until the open questions are answered.
  </Step>
  <Step title="Create the pull request." icon="4" iconType="sharp-solid" stepNumber={4} titleSize="h4">
    Click **Create pull request**, then **Yes, create it**. One click creates one pull request with every ticked draft in that entry, and the page shows its link when it's done.

    If the page stops partway, it says which step failed. Click **Finish pull request** to continue on the same branch.
  </Step>
  <Step title="Review and merge in GitHub." icon="5" iconType="sharp-solid" stepNumber={5} titleSize="h4">
    Open the pull request, check the changes and the open questions in its description, and wait for the **Mintlify Deployment** check to finish. Then merge it.
  </Step>
  <Step title="Confirm it went out." icon="6" iconType="sharp-solid" stepNumber={6} titleSize="h4">
    Within about an hour, the rows in the **Release Updates** tab change to **Published** with the date, and the announcement appears in **#help-center-announcements**.
  </Step>
</Steps>

## **Statuses in the Release Updates Tab**

| Status | What it means |
| --- | --- |
| **Draft ready for review** | Claude drafted a change and it's on the review page. |
| **Draft needs info** | A draft exists, but it has open questions to answer first. |
| **No guide change needed** | The release was checked and needs no change. The **What Was Updated** column gives the reason, for example internal-only, already covered, or not to be advertised. |
| **PR open** | A pull request exists but isn't merged yet. |
| **Published** | The pull request is merged. The date column shows when. |
| **PR closed (not merged)** | The pull request was closed without merging. |

<Note>
  Rows are matched by a hidden **Key** column, so a release keeps the same row as it moves from draft to published. Don't edit or sort the Key column.
</Note>

## **What the Drafts Follow**

- **Facts only:** every sentence comes from the release post, its thread and files, or existing guides. Anything unclear becomes a TODO in the draft and an open question, never a guess.
- **House style:** voice, terms, and layout follow `.mintlify/AGENTS.md`. New guides use Heading 2 (`## **Heading**`) for sub-titles. Edits inside an existing page keep that page's heading level.
- **Public guides only:** drafts never touch `latchel-admin/` or the What's New newsletters, and never include internal details.
- **No change needed:** internal-only releases, releases the post says not to advertise, releases already covered by a guide, and video-only posts are logged with the reason instead of drafted.

## **How to Hold an Announcement**

Merging a pull request announces it automatically. To hold one, for example until screenshots are added, ask Claude to put it on hold **before** you merge. Held pull requests are listed as on hold until you say to announce them.

Cleanup pull requests that aren't tied to a release, like formatting fixes or rewrites, are never announced.

## **Troubleshooting**

| Problem | What to do |
| --- | --- |
| GitHub says **"We couldn't merge this pull request"** | Another pull request merged first and changed the same page or menu section. Ask Claude to rebuild the pull request on the current site. It opens a fresh pull request with the same content and closes the old one. |
| **Create pull request** stopped partway | Click **Finish pull request** on the same entry. It picks up where it stopped. |
| No new entry this morning | Either there were no #product-release posts yesterday, or the Claude app was closed at 6:00 AM. The check catches up the next time the app opens. |
| A request in **#help-guide-requests** isn't tied to a release | Handle it directly. It's logged in the tracker as **Not from a release**. |
| Stray `**` or `_` showing on live pages | Ask Claude to run the stray-markup scan. It checks every public page and fixes them in one pull request. |

## **Things to Remember**

<Warning>
  - Only merging publishes a change. Creating a pull request doesn't.
  - One entry means one pull request. If two pull requests change the same page, merge one, then ask Claude to rebuild the other before you merge it.
  - Never put internal details in a public guide.
</Warning>

<Tip>
  When someone in #help-guide-requests asks about a release, check the review page first. The draft is often already there.
</Tip>
