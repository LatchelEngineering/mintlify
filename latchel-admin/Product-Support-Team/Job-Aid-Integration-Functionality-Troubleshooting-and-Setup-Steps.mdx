<Note>
  This job aid outlines how Product Support sets up, monitors, and troubleshoots integrations with AppFolio, Rent Manager, Propertyware, Yardi, and Buildium.

  It covers:

  - Initial setup of new connections
  - **Starting every integration ticket from the [Integration Health dashboard](https://app.latchel.com/admin/integration-health)**
  - Troubleshooting property, resident, and work order sync issues (including ref ID investigations)
  - Escalating through the right path: PM, Data Support, or Engineering (via the [Bug Reports form](https://app.latchel.com/admin/bug-reports))
</Note>

<Tip>
  **What changed (Sep 2026):** The admin [Integration Health](https://app.latchel.com/admin/integration-health) page is now the first stop for any integration ticket. It shows each PM's sync status, what is wrong, and the recommended next step. Pulling plugin versions and last-sync dates by SQL is now a backup, not step one.
</Tip>

<Warning>
  If the customer already has resident and property data in Latchel, do not activate an integration without consulting the Data Support team. Escalate the ticket via Wavelength into the Data Support Team space and share "**Data Migration**" as the task type. Do not proceed with the setup steps below. Data Support will manage this transition and keep you updated in the Slack thread.
</Warning>

## 3. Start Here: The Integration Health Dashboard

**Location:** Admin → Integration Health ([app.latchel.com/admin/integration-health](https://app.latchel.com/admin/integration-health))

Every integration ticket starts here. Search the PM's company name, open their row, and read the problem and recommended action before you do anything else. Include what you saw here in your ticket notes and any escalation summary.

<Note>
  **Data Support (DS) owns monitoring of this dashboard.** DS works the Failing/Silent list, takes the Data Support and Engineering actions, and logs the status of every PM in DS's integration health tracking document. **PS's role:**

  - **Handle PM-action escalations from DS.** When the recommended action needs the PM to do something (e.g., run the sync, update the extension, fix permissions or data in their PMS), DS first checks Wavelength for prior PS outreach. If there's none, DS posts a PS escalation in `#ps-escalation` with the recommended action. PS reaches out to the PM and logs it in the Wavelength ticket.
  - **Use the dashboard as a lookup tool** when a PM writes in about an integration issue, so your troubleshooting and reply reflect the current sync status.
  - **Don't take DS actions yourself** (ref ID fixes, remote-server syncs, credential checks). Send them to DS via `#data-support-requests`.
</Note>

<Info>
  - The dashboard re-checks every integration **every 15 minutes**. A row changes state when its checks change.
  - Times are shown in **your** timezone, not UTC.
  - If the dashboard disagrees with another source (the legacy Integration Health Metrics Google Sheet, or an automated "your integration has not run in 7 days" email), **trust the dashboard**.
</Info>

#### 3.1 Statuses

Click **What these mean** at the top of the page for the full definitions. In short:

| Status | What it means | What to do |
| --- | --- | --- |
| **Failing** | A whole channel is down (e.g., credentials rejected, 50% of work orders failing, a work order stuck 24 hours, 3+ extension errors in a day, or a sync many hours late). | **Act now.** This will not clear on its own. |
| **Silent** | Nothing has moved in either direction for 48 hours (72 hours for an AppFolio account the PM runs). An integration that has never synced turns Silent 7 days after it was connected. | **Act.** Confirm the account is still in use (e.g., not churned or not yet launched) before troubleshooting. |
| **Degraded** | Something is wrong, but data is still flowing (e.g., 15% of work orders failing, 10% of properties unmapped, a sync lock held 60 minutes). | **Watch.** Often clears by the next sweep. Chase it if it has been in this state for more than 24 hours. |
| **Unknown** | Our own checks could not run. | Usually our issue, not the customer's. Nothing to act on yet. |
| **Paused** | Syncing was switched off on purpose. | Nothing. It changes when someone changes the setting. |
| **Healthy** | Every check passed. | Nothing. |

#### 3.2 Reading the list

Each row shows **Company**, **Platform**, **Status**, **Problem** (the main failing check, with `+N` for additional problems), **In this state for**, and **Checked**.

Tags you'll see:

- **Latchel-managed**: Latchel runs this PM's sync on our remote server. Sync problems are ours to fix, not the PM's.
- **Frequent sync**: the plugin is told to sync on the faster cadence.
- **Escalated** / **Escalated ×2**: this problem has already been escalated to engineering. Don't escalate it again; add your ticket context to the existing thread instead.

<Warning>
  **"In this state for" only counts from when monitoring started (early Sep 2026).** A PM whose sync hasn't run since April may still show "33 days." Use **Last data seen** in the detail panel to see how long the sync has really been down.
</Warning>

#### 3.3 Reading a company's detail panel

Click the company name to open the detail panel. Work top to bottom:

1. **Header**: Platform, **Managed by** (`Latchel` or `the PM's browser`), **Frequent sync** (On/Off), **In this state for**, **Last data seen**, and **Checked**. The **Open [Company] →** link goes to the PM's Integrations tab.
2. **Problems**: each failing or degraded check, with:
   - What the check measures and **When this is flagged** (its thresholds)
   - The affected work orders, each linked, with an error **category** (e.g., Permissions) and the raw platform error
   - A recommended action box: **Recommended PM Actions**, **Recommended Data Support Actions**, or **Recommended Engineering Actions**, often with links to the relevant help article
3. **Sync schedule**: each sync (Work orders, Properties and residents, Sending to AppFolio), how often it's expected, when it last ran, and when it will be flagged.
4. **Checks passed**: expand to see everything that's healthy (e.g., "All 199 properties are linked").

<Note>
  **Latchel-managed vs. Frequent sync are separate settings.** Latchel-managed tells the dashboard we run the sync (and uses tighter thresholds). Frequent sync tells the plugin to sync every 15 minutes. A PM who runs their own sync can have Frequent sync turned on, but they'll see an extension pop-up every 15 minutes.
</Note>

#### 3.4 What each check means

| Check | What it looks at | Flagged when |
| --- | --- | --- |
| Sync enabled | Whether syncing is on for the company | Off = **Paused**; no other checks run |
| Work order sync (AppFolio) | How long ago work orders last came in | Degraded after 2 hrs, Failing after 8 (1 and 4 if Latchel-managed) |
| Property and resident sync (AppFolio) | Last full property/resident pull | Degraded after 36 hrs, Failing after 72 (28 and 48 if Latchel-managed) |
| Sending to AppFolio | Last time we pushed work order changes into AppFolio | Degraded after 4 hrs, Failing after 24 (2 and 8 if Latchel-managed) |
| Properties / Residents (other platforms) | Scheduled pulls (hourly for most platforms, every 2 hrs for Propertyware) | Shown in the Sync schedule for that company |
| Outgoing work orders | Share of recent work orders the platform rejected (each counted once, by latest attempt) | Degraded at 15%, Failing at 50% |
| Stuck work orders | Work orders that failed and haven't gone through since | Failing once the oldest is 24 hrs old |
| Unaccounted-for work orders | Work orders with no platform ID and no sync attempt ever recorded | Always an engineering path |
| Extension errors (AppFolio) | Errors the browser extension reported | Degraded at 1–2 in 24 hrs, Failing at 3+ |
| Sync lock | A sync marked "running" with no heartbeat | Degraded after 60 minutes |
| Import quality | Whether the last import landed cleanly | Failing if it failed outright, Degraded if 25%+ of rows unreadable |
| Property links | Latchel properties with no matching platform record (WOs on them can't sync) | Degraded at 10%, Failing at 40% (min. 5 unmapped) |
| Resident links | Latchel residents with no matching platform record | Degraded at 20%, Failing at 50% (min. 5 unmapped) |

#### 3.5 Follow the recommended action

The action box tells you who owns the next step:

<Tabs>
  <Tab title="Recommended PM Actions (PS)">
    Shown when the PM runs their own sync (**Managed by: the PM's browser**) or the fix is on their side (e.g., permissions or data in their PMS). **PS owns these**, usually via an escalation from DS in `#ps-escalation`.

    1. Check Wavelength for prior outreach to this PM about the same issue so we don't contact them twice.
    2. Reach out to the PM using the recommended action and linked article. For an AppFolio sync that isn't running, use the [template in section 6](#6-pm-outreach-templates).
    3. Log the outreach (date and what you asked) in the Wavelength ticket, and reply in the `#ps-escalation` thread so DS can update their tracking document.
    4. If the PM is unresponsive, escalate to their CSM.
  </Tab>
  <Tab title="Recommended Data Support Actions (DS)">
    Shown for Latchel-managed syncs and for fixes on our side (ref IDs, remote-server sync instance, credentials). **DS owns these.** For reference, DS will:

    1. Open each stuck work order and press **Sync Now** (retry) on its integration banner. Anything that goes through was a blip; anything that fails again follows the guidance in the panel. The dashboard only updates on its next check, so a fixed row won't clear right away.
    2. Read the pattern: a property shared across several failures points to **mapping** (e.g., a missing ref unit ID; see section 4.1); one error shared across all of them points to **config or permissions**.
    3. For "Check the sync instance we run for this company," check the remote-server session per section 4.2.1 (also see [How to troubleshoot a sync on the Latchel cloud device](/latchel-admin/Service-Operations/Ops-Integrations/how-to-troubleshoot-a-sync-on-the-latchel-cloud-device)).
    4. For permission errors, check whether Latchel has the PM's credentials in the software login to verify access. If the PM needs to change something, DS escalates to PS.

    If you come across one of these while working a PS ticket, check the `#data-support-requests` history first, then post there with what you found.
  </Tab>
  <Tab title="Recommended Engineering Actions">
    Shown when there's no ops path (e.g., "Unaccounted-for work orders," uncategorized errors), or when the recommended steps didn't fix it.

    1. Confirm the problem isn't already tagged **Escalated to engineering**.
    2. Use **Escalate to engineering** in the panel (DS usually does this as part of monitoring; coordinate in `#data-support-requests` before escalating from a PS ticket).
    3. **Don't re-send** work orders marked unaccounted-for until the PMS has been checked. The create may have succeeded there and failed before reporting back, so a re-send can create a duplicate.
  </Tab>
</Tabs>

<Info>
  **Not every Failing row is a real failure.** Check the PM's subscription first. Benefits-only, Basic, or Home Assistant PMs don't use Latchel maintenance, so failing work order checks are expected (a subscription mismatch, not an integration issue). For Silent PMs with no imports, confirm the account is still active with the CSM team in the PS \<> CS Sync channel. Report these, and any unclear dashboard instructions, to Ben in `#integration-health`.
</Info>

#### 3.6 Known error categories

| What you see | What it means | What to do |
| --- | --- | --- |
| **Permissions** (Buildium: "You do not have AddEdit access to Work Orders") | The syncing Buildium user can see data but can't create/edit work orders | PM grants AddEdit access to Work Orders. Then press **Refresh** on the integration or **Sync Now** on a stuck WO. Not an engineering escalation. |
| AppFolio: Latchel user has no access to the property | The Latchel user in AppFolio can't see specific properties | Ask the PM to give the Latchel user access to those properties. WOs go through on the next sync. |
| AppFolio: expired user session / AppFolio refused the create | The remote-server session logged out, or the account signed in lacks WO create/edit rights | Latchel-managed: sign the instance back into AppFolio **as the Latchel user** and confirm it can create/edit work orders. PM-run: PM re-signs in. |
| Yardi: "Yardi needs a priority" / "Could not find Priority" | That PM's Yardi database requires a priority on every WO | Escalate to engineering. It's a per-company config change; the PM doesn't need to do anything. |
| Propertyware: "Propertyware created work order … do not re-send" | The WO already exists in Propertyware; only the link back to us failed | **Do not re-send** (it will duplicate). Escalate to engineering to link it. |
| Propertyware: "Location is invalid" / "Unit ID is invalid" | Property setup issue in the PM's Propertyware (unit may be inactive or deleted) | PM fixes the property in Propertyware, then re-send from the failed-sync list. |

<Tip>
  Have feedback, a bug, or a feature request for the dashboard itself? Post it in the normal `#bug-report` or `#feature-requests` channels. Use `#integration-health` for questions about the process.
</Tip>

## 4. Troubleshooting by Scenario

#### 4.1 Property and Resident Data (All Platforms)

<Warning>
  **Check for existing and disabled data before creating anything new.** Most "missing" records already exist in Latchel, disabled or under the wrong property. Creating a new one makes a duplicate. If a property from the PM's report is in Latchel but disabled, enable it. Don't create a new one.
</Warning>

Key reports:

- **Integration report**: PM's company page → **Integrations** tab → download the property or tenant (resident) CSV. This is what the PMS sent us, including the **Ref Property**, **Ref Unit**, and **Ref User** IDs.
- **P1** (all active properties) and **R4** (resident search) queries in pgAdmin: see [Job Aid: SQL Queries](/latchel-admin/Customer-Success-Team/SQL-Queries-PGAdmin-Job-Aids/Job-Aid-SQL-Queries).

<AccordionGroup>
  <Accordion title="Property Isn't Syncing / Missing from Latchel">
    **Description:** The PM reports a property that should be in Latchel but isn't.

    <Tabs>
      <Tab title="Reconciliation Steps">
        1. **Check Integration Health.** Confirm the property/resident sync is actually running (Last data seen, Sync schedule). If it isn't, fix the sync first. The property may simply not have come over yet.
        2. **Run P1** and search for the address to confirm it's not in Latchel under a slightly different address, or disabled.
        3. **Download the integration property report** and find the property.
           - **Not in the report:** Latchel doesn't have access to it or it's hidden/inactive in the PMS. Ask the PM to check that the sync user (e.g., the AppFolio user running the sync) has access to that property or property group, and that the property is active.
           - **In the report:** note its **Ref Property ID** and **Ref Unit ID** (the first two columns in the Rent Manager CSV) and search Latchel for them.
        4. **Check for incomplete data.** If the property is in the report but not in Latchel, look for missing required fields: an address in the wrong field (e.g., in Address 2), or a missing City/State. Properties missing required address info won't sync. Example: an AppFolio PM's units didn't sync until the **State** field was entered on those units.
        5. **Next step:** if data is missing/incorrect in the PMS, ask the PM to correct it there and let it sync again rather than adding the property manually. If the data is complete and the ref IDs still aren't in Latchel after the next sync, escalate (see [section 5](#5-escalation-process)).
      </Tab>
      <Tab title="Suggested Scripting">
        Hi [PM],

        Thank you for flagging this! I took a look at [address], and it looks like this property hasn't synced over to Latchel because [the City and State fields are missing / the address is entered in the Address 2 field] in [PMS].

        Could you please update the property details in [PMS]? Once it's corrected, it will sync to Latchel automatically on the next sync. I'll keep an eye out and confirm once it's in.

        Please let me know if you have any questions!
      </Tab>
    </Tabs>
  </Accordion>

  <Accordion title="Resident Missing or Needs to Be Added (Integration PM)">
    **Description:** The PM asks for a resident to be added, but the resident isn't showing in Latchel (even under disabled residents) and Resident Modification may prevent manual creation.

    <Tabs>
      <Tab title="Reconciliation Steps">
        1. **Download the resident report** from the PM's PMS, or ask the PM for it.
        2. **Run the R4 query** and search for the resident by name.
           - **Found:** confirm they're on the correct property. If not, move them to the correct property.
           - **Not found:** continue.
        3. **Download the integration (tenant) report** from the Integrations tab and search for the resident's name.
           - **Not listed:** the resident hasn't synced. The PM needs to add/update them in their PMS.
           - **Listed:** continue.
        4. **Find the resident's Ref User** in the integration report (also note the Ref Property and Ref Unit).
        5. **Search Latchel for that Ref User.** If it exists, compare the Ref Property and Ref Unit to the property in Latchel.
           - If they match, **update the existing resident record** instead of creating a new resident.
        6. **Open the property** in the Latchel Console.
        7. **Find the resident** currently linked to that Ref User.
        8. **Update** the name, email, phone number, and any other contact info to match the integration report. Save, then confirm the record matches the report and is still linked to the correct Ref User.

        <Tip>
          **Example:** Daniel wasn't found by name with R4, but he was in the integration report. His Ref User already existed in Latchel, attached to the previous resident (Julian) at the same Ref Property/Ref Unit. The fix was to update Julian's record with Daniel's details, not create a new resident.
        </Tip>
      </Tab>
    </Tabs>
  </Accordion>

  <Accordion title="Duplicate Properties or Residents: Which Record to Keep">
    **Description:** There are multiple records in Latchel for the same property/resident (e.g., the PM reports a "Rear" unit, but none of the 3 Latchel records say "Rear").

    <Tabs>
      <Tab title="Reconciliation Steps">
        1. **Download the property report** from the Integrations tab.
        2. **Export P1** from pgAdmin.
        3. **Compare the address on both reports** and find which **ref ID** is active in the integration report. That's the record to keep.
        4. Enable the record with the correct ref ID and disable the incorrect one. Update the name/address to match the PMS if needed (e.g., add "Rear").

        **Merging rules (Data Support):**

        | Situation | Rule |
        | --- | --- |
        | Both duplicates have **different ref IDs** (even if the name/address is an exact match) | **Do not merge.** They're different records in the PMS. |
        | Only one duplicate has a ref ID | **Merge and keep the one with the ref ID.** |
        | Neither has a ref ID (non-integration PM) | **Always merge.** |

        **Tie-breakers (optional):**

        - Same status → keep the oldest record.
        - One disabled, one enabled → keep the enabled record.
        - Properties → keep the one with active residents; if both have residents, keep the oldest.
        - Residents → keep the contact details that match the PM's report; update if needed.

        5. If you're unsure which record to keep, or the fix is larger than a few records (e.g., a PM merged properties in their PMS), request help in `#data-support-requests` with the ref IDs you found.
      </Tab>
    </Tabs>
  </Accordion>

  <Accordion title="Property Shows Disabled but Is Active in the PMS">
    **Description:** A property is disabled in Latchel (e.g., a resident can't use a benefit), but the PM confirms it's active on their side and the sync is up to date.

    <Tabs>
      <Tab title="Reconciliation Steps">
        1. **Integrations never re-activate a disabled property.** Status only syncs from active to inactive.
        2. Check the property's **activity log** to see when and how it was disabled (inactive in the PMS at some point, or disabled manually).
        3. Confirm the property is in the integration property report as active, and that there isn't another copy of it (e.g., under a different PM account). If there's a duplicate, follow the duplicate steps above.
        4. **Enable the property in the Latchel UI.**
      </Tab>
      <Tab title="Suggested Scripting">
        Hi [PM],

        Thanks for confirming! The property had been marked inactive in Latchel, and our integration only syncs status changes from active to inactive, so reactivating it in [PMS] doesn't carry over automatically. I've re-enabled it on our side, so you're all set.

        Let us know if you run into anything else!
      </Tab>
    </Tabs>
  </Accordion>

  <Accordion title="Work Order Shows Synced but Isn't in the PMS (Ref ID Mismatch)">
    **Description:** A work order shows as successfully synced, but the PM can't find it in their PMS by WO number or reference job ID.

    <Tabs>
      <Tab title="Reconciliation Steps">
        1. Check Integration Health for failing or stuck work orders on that PM.
        2. Compare the property's **ref property ID** and **ref unit ID** in Latchel against the PMS (integration report or the PM's property export).
           - Example: in Propertyware the property had Ref Property `19016125172` and Ref Unit `2008088596`, but in Latchel both the property ID and ref property ID were `2008088596`.
        3. Check for a disabled or duplicate property that already has the correct ref ID before changing anything.
        4. If there's a mismatch and no duplicate, request the ref ID correction in `#data-support-requests`.
        5. If the ref IDs match, the sync is current, and the WO still isn't in the PMS, submit a [bug report](https://app.latchel.com/admin/bug-reports).
      </Tab>
    </Tabs>
  </Accordion>
</AccordionGroup>

#### 4.2 AppFolio Troubleshooting

- Refer to [(CS/Admin) How To: Troubleshoot the Latchel Plug-in](https://latchel.atlassian.net/wiki/spaces/CS/pages/795115811)
- **Always check Integration Health first:** Managed by, Last data seen, Extension errors, and the Sync schedule answer most "is the sync running?" questions without SQL.
- **The AppFolio sync only runs while an AppFolio tab is open** in the browser of whoever runs it (the PM, or our remote server for Latchel-managed PMs).
- For work orders that aren't exporting to AppFolio, see [How to: Resolve AppFolio Work Order Export Failures](/latchel-admin/Service-Operations/Ops-Integrations/how-to-resolve-appfolio-work-order-export-failures).
- **Investigating any AppFolio issue:** check the **software login** spreadsheet (AppFolio tab) for the PM's credentials. If we have them, log in to AppFolio yourself in a regular Chrome browser to look at the property, resident, or work order directly, instead of asking the PM for reports or examples. The spreadsheet has credentials for many more PMs than we run the sync for.

#### 4.2.1 Latchel-Managed AppFolio Syncs (Remote Server)

For PMs tagged **Latchel-managed** on Integration Health, Latchel runs the AppFolio sync on the PM's behalf from our remote server, accessed through **TeamViewer**. Each PM has its own Chrome profile there, signed in to AppFolio and the Latchel Data Sync extension.

<Warning>
  **The remote server is only for PMs whose sync Latchel runs.** Don't create profiles for, or run syncs for, any other PM on the remote server. To investigate a PM that runs its own sync, use their software login credentials in your own browser.
</Warning>

<AccordionGroup>
  <Accordion title="Daily Check and Re-running a Sync">

### **7. Troubleshooting Queries**

Use these when Integration Health doesn't answer the question. For property (P1) and resident (R4) lookups, see [Job Aid: SQL Queries](/latchel-admin/Customer-Success-Team/SQL-Queries-PGAdmin-Job-Aids/Job-Aid-SQL-Queries).

SQL query to see the last time the integration (any integration) ran successfully:

```sql lines
select i.company_id, c.name, i.type, i.status, i.total_rows, i.created_at, i.source
FROM public.import i
JOIN public.company c
ON i.company_id = c.company_id
WHERE i.company_id = ####
ORDER by i.created_at desc
LIMIT 10
```

SQL query to see which version of the Latchel plugin the PM is running (AppFolio clients):

```sql lines
SELECT al.created_at, al.plugin_version 
FROM appfolio_log al 
WHERE al.pm_company_id = #### 
ORDER BY al.created_at DESC 
LIMIT 1
```

SQL query that flags duplicate work orders. It should return zero results. If it returns results, report it through the [Bug Reports form](https://app.latchel.com/admin/bug-reports) for urgent attention. Replace `549` with the PM's company ID.

```sql lines wrap
SELECT j.ref_job_id, j.created_at, i.settings->>'last_sync_time' as last_sync_time FROM job j 
JOIN property p ON p.property_id = j.property_id 
JOIN company c ON c.company_id = p.pm_company_id 
JOIN integration i ON i.pm_company_id = c.company_id 
JOIN pm_company_settings pcs ON pcs.pm_company_id = c.company_id 
WHERE c.company_id = 549 AND j.ref_job_id IS NULL AND j.created_at < DATE(i.settings->>'last_sync_time') AND j.created_at > pcs.integration_sync_date;
```

SQL query to list PM companies flagged as Latchel-managed:

```sql lines
SELECT
    c.company_id,
    c.name AS company_name,
    i.integration_id,
    i.platform,
    i.status
FROM integration i
JOIN company c
    ON i.pm_company_id = c.company_id
WHERE i.settings ->> 'is_latchel_managed' = 'true';
```
