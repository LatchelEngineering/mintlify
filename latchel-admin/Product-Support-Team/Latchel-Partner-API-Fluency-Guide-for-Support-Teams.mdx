## Part 1: How to Use This Guide

This guide has two jobs. First, it teaches you the core concepts behind APIs so you can understand what customers are asking. Second, it gives you a complete reference for Latchel's Partner API (PAPI) so you can look up the right answer quickly.

By the end, you should be able to:

- Explain what an API is and how it works using non-technical language
- Navigate the Latchel PAPI documentation yourself at [papi.latchel.com](https://papi.latchel.com/api-docs/papi/)
- Identify which endpoint a customer needs based on their question
- Answer the most common API questions without escalating
- Know exactly when something genuinely needs an engineer

<Note>
  **How to use:** Read Parts 2–3 once to build your foundation. Use Part 4 as an ongoing lookup reference. Keep Part 5 (the question framework) and Part 6 (when to escalate) bookmarked. Part 8 has practice scenarios from the PS API training.
</Note>

## Part 2: API 101 — Core Concepts

### 2.1 What is an API?

API stands for Application Programming Interface. The easiest way to think about it: **an API is a waiter at a restaurant.**

You (the customer) want food from the kitchen. You don't walk into the kitchen yourself — you tell the waiter what you want, the waiter goes to the kitchen, and comes back with your order.

In tech terms: a customer's internal system (the diner) wants data from Latchel (the kitchen). The customer's system makes a request to the Latchel API (the waiter), and the API returns the data (delivers the food).

Latchel's Partner API (PAPI) is how customers can access their Latchel data — vendors, properties, work orders, tenants, invoices, and more — from their own tools and systems.

### 2.2 What is REST and Why Does it Matter?

Latchel's PAPI is a REST API. This means requests are made over the web using standard HTTP calls — the same technology your browser uses to load a webpage. There are five types of actions (HTTP methods):

| Method | What it does |
| --- | --- |
| **GET** | Read data. Retrieve a list of vendors, look up a specific job, etc. GET requests never change data. |
| **POST** | Create new data. Create a new job, add a new property, etc. |
| **PUT** | Replace / fully update an existing record. |
| **PATCH** | Partially update an existing record — change just one or two fields. |
| **DELETE** | Remove a record permanently. |

<Note>
  **Support tip:** Most customer questions are about GET requests — they want to read data out of Latchel. If a customer asks how to pull a list of something, it's always a GET.
</Note>

### 2.3 What is an Endpoint?

An endpoint is a specific URL that performs a specific action. All Latchel endpoints start with: `https://papi.latchel.com/v1/`

Examples:

- `https://papi.latchel.com/v1/vendor-companies` → List all vendors
- `https://papi.latchel.com/v1/jobs` → List all jobs/work orders
- `https://papi.latchel.com/v1/properties/123` → Get details of property ID 123

The `{placeholders}` in documentation (like `/properties/{property_id}`) mean the customer replaces the placeholder with a real ID from their account.

### 2.4 What are Parameters?

- **Query parameters** — appended to the URL after a `?` to filter, sort, or paginate results. Example: `/jobs?status=open&page=2` returns open jobs on page 2.
- **Path parameters** — embedded in the URL to identify a specific record. Example: `/jobs/456` retrieves job number 456.

### 2.5 What is Authentication?

Latchel uses **API Key authentication**. Every request must include an API key in the request header. The key tells Latchel which account the request is coming from.

Important things to know:

- Each property manager generates their own API key from their Latchel dashboard (Account Settings → Integrations). Guide: [How to Generate an API Key](https://help.latchel.com/s/topic/0TO5e000000h9wqGAA/How-to-Generate-an-API-Key).
- Re-generating immediately invalidates the old key — the customer must update any integrations using the old key.
- Latchel does **not** currently support scoped (read-only) API keys — all keys have full access.
- For API-specific technical issues: [tech@latchel.com](mailto:tech@latchel.com)

### 2.6 Rate Limits

**600 requests per API key, per 10-minute window.** When the limit is hit, the API returns HTTP 429 (Too Many Requests).

| Response Header | What it means |
| --- | --- |
| `x-ratelimit-limit` | Total requests allowed |
| `x-ratelimit-remaining` | Requests still available before hitting the limit |
| `Retry-After` | When the next retry will succeed (returned with a 429) |
| `X-RateLimit-Reset` | When the throttling resets as a whole (returned with a 429) |

<Note>
  **Support tip:** If a customer reports 429 errors, ask how many requests per minute they're making. Advise them to add delays between batches, spread the sync over time, and use larger pages (see 2.7) so they need fewer requests.
</Note>

### 2.7 Pagination

List endpoints return **one page at a time**, not all records at once. If a customer says they're only seeing partial data, pagination is usually the reason.

- `page` — which page to return. Iterate through pages to get everything.
- `per_page` — page size, **1 to 500, default 10**. A `per_page` outside that range returns **HTTP 422**.
- Requesting a large page (up to 500) is the fastest way to pull a big portfolio within the rate limit.

<Note>
  **Support tip:** "I only get 10 records back" almost always means they haven't set `per_page` and aren't paging. Tell them to set `per_page` (up to 500) and loop through `page`.
</Note>

### 2.8 Delta Sync (Only Changed Records)

`GET /properties`, `GET /tenants`, and `GET /properties/{property_id}/tenants` accept **`updated_at_start_date`** (an RFC 3339 date-time) to return only records changed at or after that time.

- A tenant counts as changed when their own details, their contacts (email/phone), or their link to a property (move-in/out dates, active status) change.
- Recommended pattern: record the time a sync starts, then pass it as `updated_at_start_date` on the next sync.
- `GET /jobs` has a filter with the same name.

<Note>
  **Support tip:** If a customer is re-pulling their entire portfolio on every sync (and hitting rate limits), point them to delta sync.
</Note>

### 2.9 Environments: Production vs. Testing

| Environment | Base URL | Notes |
| --- | --- | --- |
| **Production (live)** | `https://papi.latchel.com/v1/` | Real account data. Use for actual integrations. |
| **Testing / Sandbox** | `https://latchel-demo.com/v1/` | Demo data only. Requires a separate development API key. Data isn't guaranteed to persist. Safe for testing. |

### 2.10 Field Inheritance

Some fields are marked `[INHERITABLE]`. They cascade down: **Company → Portfolio → Property**. If a field is set at the Company level, all Portfolios and Properties inherit it automatically unless overridden.

### 3.3 Step-by-Step: Looking Up Any Endpoint

1. Go to [papi.latchel.com/api-docs/papi/](https://papi.latchel.com/api-docs/papi/)
2. Identify the data type the customer is asking about (vendors, jobs, properties, tenants, etc.)
3. Click the matching category in the left sidebar (or search with ⌘K)
4. Scan the endpoint list. Find the one matching the action (GET for reading, POST for creating, etc.). Click "Show N more..." if the list is cut off.
5. Open the endpoint to see details
6. Read the Parameters section to answer questions about filters, pagination, required fields
7. Read the Response section to confirm what fields are returned
8. Share the direct link to that endpoint with the customer

### 4.19 Webhooks (Push Notifications — Separate from PAPI)

In addition to the pull-based PAPI endpoints, Latchel supports **Webhooks**. Webhooks are push notifications — Latchel sends data to the customer's system automatically when something changes.

Supported webhook events:

- Jobs (work order created or updated)
- Portfolios (created or updated)
- Tenants/Residents (created or updated)

Webhook documentation is separate from PAPI and is available in the Help Center (search "Webhooks").

### Step 4 — Answer the Common Follow-Ups

| Customer question | Answer |
| --- | --- |
| How do I authenticate? | API key in the request header. Generate at Account Settings → Integrations in the Latchel dashboard ([guide](https://help.latchel.com/s/topic/0TO5e000000h9wqGAA/How-to-Generate-an-API-Key)). |
| Why am I only getting some records? | Pagination. Set `per_page` (1–500, default 10) and iterate through `page`. |
| I'm getting a 422 on a list call | `per_page` is outside 1–500. |
| Why am I getting 429 errors? | Rate limit hit. Max 600 requests/10 minutes per key. Add delays, use bigger pages, and use delta sync. |
| Can I only pull what changed? | Yes, for properties and tenants: `updated_at_start_date`. Jobs have a filter with the same name. |
| Can I filter to only active/recent records? | Check the parameters for that specific endpoint — most list endpoints support filters. |
| I need a read-only key | Not available. Latchel does not support scoped API keys. Escalate to CSM if a blocker. |
| Can I test without affecting live data? | Yes. Use latchel-demo.com/v1 with a separate development API key. |

## Part 6: When to Escalate

### Handle It Yourself

- Any question covered in Parts 4 or 5 of this guide
- Questions about generating or re-generating an API key
- Rate limit questions — explain the limit and advise on pacing
- Pagination and delta sync questions — point to the docs for that endpoint
- Requests for read-only API keys — explain not available, note to CSM if a blocker
- Questions about Analytics+ as an alternative to the API

### Escalate to Engineering ([tech@latchel.com](mailto:tech@latchel.com))

- The API is returning incorrect or missing data for the customer's account
- A customer's API key is not working after re-generation
- An endpoint described in the docs is not behaving as documented
- The customer is reporting a consistent API error (4xx or 5xx) not explained by rate limits, pagination, or auth issues
- A customer wants a new API feature (new endpoint, read-only keys, new filter options)
- Data discrepancies between what the API returns and what appears in the dashboard

<Tip>
  For internal bug reports on API behavior, you can also use the [Bug Reports form](https://app.latchel.com/admin/bug-reports). Include the endpoint, the request the customer made (never their API key), the response/status code, and the account.
</Tip>

### Escalate to CSM ([success@latchel.com](mailto:success@latchel.com))

- A customer wants to discuss API access as part of a broader account conversation
- A customer says a missing API feature is causing them to consider churning
- Requests for a demo/sandbox account or separate development API key

### Key HTTP Status Codes

| Code | Meaning | What to do |
| --- | --- | --- |
| 200 | OK — request succeeded | All good |
| 204 | Success, no content returned (e.g., after a merge) | All good |
| 401 | Unauthorized — API key missing or invalid | Check the API key; have customer re-generate if needed |
| 403 | Forbidden — the request isn't allowed | Confirm the record belongs to the customer's account; escalate if it does |
| 404 | Not found — the ID in the request does not exist | Verify the ID is correct for this account |
| 422 | Invalid request (e.g., `per_page` outside 1–500) | Check the parameters against the docs |
| 429 | Too many requests — rate limit exceeded | Add delays; advise on pacing. Max 600/10 minutes. |
| 500 | Server error | Escalate to [tech@latchel.com](mailto:tech@latchel.com) |

## Part 8: Practice Scenarios

These come from the PS API training. Try answering before you open each one.

<AccordionGroup>
  <Accordion title="A customer wants to pull a list of all their work orders via the API.">
    **GET /jobs** — work orders are called "Jobs." Remind them to use filters (status, date, property) and pagination (`per_page` up to 500, loop through `page`) for large accounts.
  </Accordion>

  <Accordion title="A customer keeps getting HTTP 429 errors.">
    They've exceeded 600 requests per key per 10-minute window. Ask how many requests per minute they're making, and advise adding delays between batches or spreading the sync over time. Bigger pages and delta sync (`updated_at_start_date`) cut the number of requests. They can watch the `x-ratelimit-remaining` and `Retry-After` headers.
  </Accordion>

  <Accordion title="A customer asks whether they can see the full timeline of status changes on a work order.">
    Yes — **GET /jobs/\{job_id\}/history/state** returns a log of all status transitions (the audit trail) for that job.
  </Accordion>

  <Accordion title="A customer says they only ever get 10 records back.">
    That's the default page size. Set `per_page` (1–500) and iterate through `page` until no more results come back. A `per_page` over 500 returns a 422.
  </Accordion>

  <Accordion title="A customer re-pulls every resident nightly and wants something lighter.">
    Use delta sync: save the time each sync starts, and on the next run call **GET /tenants** (or **GET /properties/\{property_id\}/tenants**) with `updated_at_start_date` set to that time. Only changed residents come back.
  </Accordion>

  <Accordion title="A customer asks for a read-only API key for a contractor.">
    Not available — all Latchel API keys have full access. If it's a blocker, note it to the CSM. Remind them that re-generating a key invalidates the old one immediately.
  </Accordion>
</AccordionGroup>
