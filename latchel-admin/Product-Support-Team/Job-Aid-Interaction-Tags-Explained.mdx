We now classify every ticket using three fields — **Category**, **Attributes**, and **Tags** — instead of a single tag list. Each field answers a different question about the interaction, and together they give a complete picture: how it reached us, what it was about, and what it drove.

## How the Three Fields Work Together

| Field | Question It Answers | Selection | Required? |
| --- | --- | --- | --- |
| **Category** | How did this ticket reach us? | Single-select | Always |
| **Attributes — Topic** | What was the ticket about? | Single-select | Always |
| **Attributes — Root Cause** | Why did it happen? | Single-select | If applicable |
| **Tags** | What did this interaction drive or produce? | Multi-select | Apply as many as apply |

A typical ticket gets tagged in this order:

1. **Category** — pick the one value that describes how the ticket arrived (a PM texted in, an SP called, an automation flagged it, and so on).
2. **Attributes — Topic** — pick the one Attribute/Value pair that best describes what the ticket was actually about (WO Coordination, Invoicing & Payments, Appfolio, and so on).
3. **Attributes — Root Cause** — if something went wrong, pick the one value that explains why (SP Performance, Platform Defect, PM Action or Delay, and so on). Skip this if nothing went wrong — a routine question doesn't need a Root Cause.
4. **Tags** — select every outcome tag that applies (Resolved by PS, Bug Filed, CSM Handoff, and so on). This is independent of Topic: crossing Topic against Tags is what lets us see, for example, which topics generate the most bugs or escalations.

<Info>
  **Topic** and **Tags** are independent of each other on purpose. Topic is what the ticket was _about_; Tags are what the interaction _drove_. Crossing the two is where our reporting on "which topics cause the most escalations/bugs/churn risk" comes from.
</Info>

## CATEGORY — How We Receive the Ticket

Category is new: it didn't exist before, and no other field captured how a ticket reached us. Pick exactly one value.

| Value | Counts in Reporting? | Use It When |
| --- | --- | --- |
| **PM Inbound** | Yes | A property manager or their staff contacted us. |
| **Owner Inbound** | Yes | A property owner contacted us directly, including via NOMAD and RentRedi. |
| **Resident Inbound** | Yes | A resident or tenant contacted us. |
| **Service Provider Inbound** | Yes | A vendor or SP contacted us. Mostly invoices, estimates, and scheduling. |
| **Partner / Platform Inbound** | Yes | A platform partner or integration contacted us — Appfolio, Rent Manager, and similar acting on their own (not a service provider). |
| **Latchel Ops Escalation** | Yes, reported separately | A Latchel associate asked PS to decide something. |
| **Latchel Outbound** | Yes, flagged separately | We started the conversation: verification requests, scorecards, CSM outreach. Real work, but not a customer-initiated contact. |
| **Not Actionable** | No, excluded | Spam and survey outbound. No Tag or Attribute is needed — Category alone is enough. |

## ATTRIBUTES — What the Ticket Is About

Attributes are new. There are two levels: **Topic** (always required) and **Root Cause** (only if something went wrong).

### Level 2: Root Cause — Why It Happened

Add a Root Cause only when something went wrong and PS needed to explain why. Skip it for routine, no-fault interactions.

| Root Cause | Definition |
| --- | --- |
| **SP Performance** | The service provider did not perform: missed appointments, went over budget without approval, poor workmanship, took payment directly, unresponsive to follow-ups. |
| **Latchel Associate Action** | A Latchel associate didn't follow an SOP, job aid, critical note, or pre-dispatch instruction, or handled the contact poorly. |
| **Automation or Workflow Behaviour** | Harmonia, Autopilot, an action set, or an AI step behaved as configured but produced the wrong outcome. |
| **Platform Defect** | A genuine software defect. Requires a linked bug report — pair with the **Bug Filed** tag. |
| **Integration or Third-Party Platform** | Data failed to move between the PMS and Latchel, or an external platform caused the failure. |
| **Account Configuration** | The account's own settings produced the outcome: severity settings, budget limits, intake rules, coverage, action sets. |
| **PM Action or Delay** | The property manager acted late, acted incorrectly, or gave unclear or conditional instructions. |
| **Owner Action or Delay** | The owner acted late, acted incorrectly, or disputed a valid charge. |
| **Resident Action or Delay** | The resident was unresponsive, cancelled, submitted incorrectly, or the complaint was not valid. |
| **Knowledge Gap** | The handling failed because the PM lacked platform knowledge, took the wrong action in the dashboard, produced the wrong outcome, etc. |
| **Undetermined – DD Requested** | The failure is real but the cause can't be established in triage. A Deep Dive has been opened — pair with the **DD Requested** tag. |

## TAGS — What the Interaction Drove

Tags describe the outcome — what the interaction produced, not what it was about. They're multi-select and independent of Attributes: apply every tag below that fits, even if that means several tags on one ticket.

| # | Tag | Apply It When |
| --- | --- | --- |
| 1 | **Resolved by PS – Confirmation Received** | PS answered or fixed it with no handoff and no follow-on ticket, with PM info or confirmation. |
| 2 | **Resolved by PS – Bias for Action** | PS answered or fixed it with no handoff and no follow-on ticket, without PM confirmation — used judgment and expertise to decide. |
| 3 | **Open Issue – Unresponsive PM** | PS couldn't resolve without PM input. Bias for action was too risky, but not critical enough for a CSM escalation. |
| 4 | **Config Change Made** | A setting was changed on the account as a result of this interaction. |
| 5 | **Help Guide Gap** | No Help Guide existed, or the existing one was wrong. |
| 6 | **SOP Gap** | An internal SOP or job aid was missing or outdated. |
| 7 | **Bug Filed** | A bug report was raised. Requires a linked ticket reference. |
| 8 | **Feature Request Filed** | A feature request was logged. |
| 9 | **Data/Eng Request Filed** | Routed to the Data team, BI team, or Engineering for action. |
| 10 | **Churn Risk** | The contact contained a cancellation signal, a legal threat, or explicit dissatisfaction with the relationship. |
| 11 | **Repeat Contact** | The same party has contacted about the same underlying issue before. |
| 12 | **CSM Handoff** | Passed to the Customer Success Manager. |
| 13 | **DD Requested** | A Deep Dive was opened off the back of this interaction. |
| 14 | **Praise** | The contact contained positive feedback about Latchel or an associate. |
| 15 | **Routed to PM (Out of Scope)** | Correctly declined and redirected to the property manager. |
| 16 | **Agent Coaching Flagged** | Raised for associate coaching. Separates quality signal from customer outcome. |
| 17 | **Reimbursement or Credit Issued** | A proprietary benefit, credit, or fee waiver was granted. |
| 18 | **Automated Alert Duplicate** | One of several near-identical machine alerts in a burst. Lets us count incidents, not alerts. |
